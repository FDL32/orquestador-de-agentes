## 2. Propuesta de configuracion de esfuerzo para modelos nan/*

**Objetivo del usuario:** poner los modelos nan al maximo esfuerzo que cada canal
permita, motivado por evidencia ya en memoria
(`obs-fs-reading-receipt-does-not-certify-correct-reasoning`) de que gemma4 (y
potencialmente otros modelos nan) fallan en tareas de conteo/consistencia interna
cuando corren con razonamiento minimo -- hipotesis de este piloto: el parametro de
esfuerzo nunca se habia fijado explicitamente en ninguno de los canales tradicionales.

**Hallazgo (verificado, no asumido): NINGUN canal tradicional del motor fija esfuerzo
para nan hoy.**
- Canal ensemble/api (`scripts/ensemble_dispatch.py:1387`): el body HTTP fija
  `temperature: 0` + `max_tokens`, SIN ningun campo de `reasoning_effort`. No hay
  evidencia en el repo de que la API de nan.builders acepte ese campo -- sin
  verificar empiricamente, no se propone cambiarlo a ciegas.
- Canal Kilo CLI (backend `kilo` de `.agent/config/agents.json`, usado en el protocolo
  tradicional de 4 capas): `args` = `["run", "--auto", "--format", "json"]`, SIN el flag
  `--variant`. Hallazgo accionable: `kilo run --help` documenta
  `--variant <string>` como "model variant (provider-specific reasoning effort, e.g.,
  high, max, minimal)" -- existe en el CLI, simplemente no se usa hoy en la config del
  motor.
- Canal nativo T3 `acpRegistry_kilo` (`delegate_task`): expone `options: effort` (
  `none|low|medium|high|xhigh|max`, default `none`) y `mode` (`code|ask|debug|
  orchestrator|plan`, default `code`) -- descubierto por el subsistema Supervisor 2.
- Canal nativo T3 `opencode` (`delegate_task`, alternativa a `acpRegistry_kilo`, ver
  Seccion 3): expone `options: variant` (`none|low|medium|high|max`, SIN `xhigh`) y
  `agent` (`build|plan`, default `build`) -- mismo concepto que `--variant` de Kilo
  CLI, nombre de parametro COHERENTE con el CLI, pero DISTINTO del `effort` de
  `acpRegistry_kilo`.

**Propuesta concreta:**
1. Canal nativo T3 (cualquiera de los dos proveedores): fijar `effort: max` (en
   `acpRegistry_kilo`) o `variant: max` (en `opencode`) por defecto para TODO despacho
   de un modelo nan/* en el protocolo trio, salvo que el rol declare lo contrario.
   Riesgo declarado: `max` puede aumentar latencia/coste de forma no lineal; sin medir
   aun cuanto. Mitigacion: medir latencia ANTES/DESPUES en el primer vuelo real que lo
   adopte, no asumir que es gratis.
2. Canal Kilo CLI (4 capas tradicional): anadir `--variant max` (o `high` si `max`
   resulta inestable para algun modelo concreto) a `args` del backend `kilo` en
   `agents.json`. Requiere prueba empirica previa (`kilo run --variant max -m
   nan/<modelo>` por cada uno de los 4 modelos del trio) antes de adoptarlo como
   default global, porque no todos los modelos declaran necesariamente soporte real
   para cada valor del enum (el enum es de la PLATAFORMA proveedora, no garantia de
   efecto por modelo).
3. Canal ensemble/api (bucles): NO se propone ningun cambio todavia. Se abre
   como investigacion separada: verificar si api.nan.builders acepta un campo
   `reasoning_effort` (o equivalente) en el body, con un smoke test de un solo perfil
   antes de generalizar. Cambiar `ensemble_dispatch.py` sin esa verificacion seria
   accionar a ciegas sobre un sistema compartido por TODOS los bucles de gobierno del
   motor -- blast radius alto, fuera de proporcion para este piloto.

## 3. Propuesta de resiliencia: cadena de fallback entre proveedores (idea del usuario)

Motivado directamente por F-NATIVA-4: si el catalogo de UN proveedor T3 nativo puede
perder modelos nan/* a mitad de vuelo sin aviso previo (confirmado: `acpRegistry_kilo`
lo hizo), un vuelo autonomo necesita un plan B que no dependa de la supervision humana
en caliente para notarlo y corregirlo.

**Cadena de fallback propuesta (verificada manualmente en esta sesion, no automatizada
todavia):**
1. Primario: `providerInstanceId: "opencode"` (768 modelos, confirmado con los 4
   modelos exactos del trio: `nan/qwen3.8-flash`, `nan/qwen3.6`, `nan/glm5.3-flash`,
   `nan/gemma4`). Parametro de esfuerzo: `variant`.
2. Secundario: `providerInstanceId: "acpRegistry_kilo"` (256 modelos; HOY sin
   nan/*, pero es otro proceso/registro independiente de `opencode` -- puede
   recuperarse de forma independiente). Parametro de esfuerzo: `effort`.
3. Terciario (ultimo recurso, fuera del canal T3 nativo): Kilo CLI directo via
   Bash (`kilo.cmd run --auto --format json -m <modelo> --variant max`), el mecanismo
   TRADICIONAL que esta serie de pilotos evaluaba sustituir. Confirmado funcionando en
   esta misma sesion con un probe directo. Es el fallback MAS resiliente (bypassa T3
   por completo) pero reintroduce las fricciones F1/F2 originales (deteccion de
   liveness fragil en Windows, ya mitigada por WOT-2026-104m) que esta serie de pilotos
   queria evitar -- por eso va en tercer lugar, no primero.

**Mecanismo de deteccion de fallo propuesto (no implementado aun, solo diseno):** un
`delegate_task` que devuelve el error estructurado `model_unavailable` (codigo ya
observado en esta sesion, no inventado) es la senal de pasar al siguiente escalon de la
cadena. Cualquier OTRO tipo de error (timeout, cuota) NO debe disparar el fallback de
proveedor -- son fallos distintos con remedios distintos (reintento, espera), y
confundirlos podria enmascarar una cuota agotada como si fuera un proveedor caido.

**Limite declarado:** esta cadena de 3 escalones NO esta cableada en ningun script del
motor todavia. Es un patron MANUAL que el Orquestador aplico una vez en esta sesion
(paso 1->2 cuando fallo `acpRegistry_kilo`). Cablearla (que el propio protocolo de
despacho del trio reintente automaticamente escalon por escalon) es trabajo futuro,
candidato a ticket propio si el bucle DESIGN_REVIEW lo aprueba.
