# WOT-2026-112c — auditoría D2b, Paso 0

## Alcance

Esta es una auditoría de evidencia, no una propuesta de política. No modifica
`scripts/check_worktree_topology.py`, sus hooks ni la prosa normativa.

## Método reproducible

Se censaron las referencias locales con:

```text
git for-each-ref --format='%(refname:short)' refs/heads/FDL32
git log <rama> --grep='WOT-2026-' --format='%H|%ad|%s' --date=short
git worktree list --porcelain
```

También se buscó evidencia textual de `check_worktree_topology.py`,
`WORKTREE_GUARD_BYPASS`, `--allow-diagnostic` y de las rutas `_dev`/`flight/`
en los artefactos locales. La unidad de conteo es la referencia de rama, no el
número de commits: un mismo cierre puede estar alcanzable desde varias ramas.

## Resultado del censo

- Se encontraron **25 referencias locales `FDL32/*`**.
- **24/25** tienen al menos un commit cuyo asunto contiene `WOT-2026-`.
- La rama sin coincidencia es `FDL32/vuelo-20261018c`.
- Entre las ramas con cierres WOT, los nombres observados son nombres directos
  de sesión/vuelo (`FDL32/104hj-4capas-20261018`,
  `FDL32/agents-md-*`, `FDL32/palanca-a-continuacion-20261021`,
  `FDL32/vuelo-*`, `FDL32/repo-audit-*`, etc.).
- En `git worktree list --porcelain` **no aparece ningún worktree de cierre
  WOT cuyo directorio sea `_dev` ni `flight/<sufijo>`**. Sí aparece el
  worktree no-WOT `C:/Users/fdl/Proyectos_Python/orquestador_de_agentes_dev`,
  asociado a `main`; no se cuenta como cierre WOT de una rama `FDL32/*`.
- Varias referencias `FDL32/*` no tienen un worktree activo en el inventario
  actual; por tanto, la ausencia de su ruta no prueba dónde se creó cada
  commit histórico.

## Qué permite afirmar la evidencia

La evidencia actual sí permite afirmar que los cierres WOT visibles en ramas
`FDL32/*` **no quedaron alojados en worktrees nombrados `_dev` ni
`flight/<sufijo>`**. La forma observable es una rama directa de sesión/vuelo,
o una referencia sin worktree activo.

No permite afirmar, para cada commit, si `check_worktree_topology.py` se ejecutó
y bloqueó, si se ejecutó desde otro cwd, si se usó un bypass, o si simplemente
no se ejecutó. No hay en el censo un recibo por commit con cwd, `--ticket`,
resultado y código de salida; tampoco hay una evidencia local completa que
relacione cada cierre con un evento del guard. Por ello, la cifra verificable
de “evasiones del guard” es **indeterminada**, no cero.

## Conclusión Paso 0

La respuesta factual es: **no se usaron de forma observable `_dev` ni
`flight/<sufijo>` para las ramas de cierre `FDL32/*` presentes; se usaron ramas
directas de sesión/vuelo o no existe ya un checkout activo**. El mecanismo
exacto (guard omitido, guard ejecutado desde cwd incorrecto o bypass) queda sin
probar con los artefactos disponibles. Esta auditoría no decide si el guard
debe relajarse o mantenerse estricto.
